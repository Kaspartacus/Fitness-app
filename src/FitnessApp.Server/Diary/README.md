# Private diary operations

This feature remains in the existing hosted application. Apply migration `20261021120000_AddPrivateDiary` with the existing documented EF migration procedure before serving the new version outside Development. Stop the server and back up the database and complete key ring first. Rollback removes all diary rows, protection hashes, grants and cleanup progress; restore a matching backup if rollback must preserve diary data.

## Required key storage

Set `DataProtection__KeyRingPath` through the existing environment/User Secrets configuration to a persistent private directory **outside the checkout and published application**, for example `/var/lib/fitnessapp-private/keys`. The tracked legacy `App_Data/data-protection-keys` default is rejected at startup. Development also needs the external-path override; User Secrets are supported by the existing Server project. Do not add key files, secrets or real diary content to the repository.

For an existing installation, stop the server, back up and move the **entire existing** Data Protection ring to this location, retain application name `FitnessApp`, then change the configuration. Do not initialize an empty replacement: the same ring also protects existing password-reset/session material. Mount the location persistently across deployments and restarts, restrict access to the application account, and use encrypted host storage/backups. Explicit filesystem persistence does not itself encrypt the key XML files; use deployment-managed disk encryption or configure the framework's certificate/vault protection if required by the host. Never print key contents in diagnostics.

Before accepting requests, startup authenticates and decrypts every unexpired diary entry with the configured ring and established diary purpose, streaming ciphertext without tracking rows or retaining plaintext. An empty, unrelated, incomplete, revoked or otherwise unusable ring stops startup with a constant restore instruction; expired entries are excluded using the application clock. A key becoming unavailable after startup causes affected reads and updates to fail closed with a generic error; unreadable content is never replaced with blank text. This is an availability safeguard, not a substitute for a verified restore procedure. Database backups without their corresponding keys cannot recover diary text. Keep database and key backups consistent and test restoring them together in a private environment using synthetic content.

ASP.NET Core Data Protection supplies authenticated encryption and automatic active-key rotation (normally every 90 days). Old entries retain their original key references; retain **all old keys** while any live entries or restorable backups depend on them. Never delete/revoke old keys as routine rotation. Planned compromise response needs an explicit operator-led restore/re-encryption/backup decision; this feature does not implement a bulk re-encryption tool. Do not change the application discriminator or diary purpose/version during routine deployment.

## Privacy and gates

This is **server-side encryption at rest**, not end-to-end encryption. The application server can decrypt entries. Only ciphertext, owner/date, an optimistic version and a fixed expiry instant are persisted for entries; there are no plaintext draft, search, snippet or content-presence columns. Reminder checks decrypt only today's row transiently. Do not enable EF sensitive-data logging, request/response body logging, plaintext exports or telemetry capture for diary routes. The existing structured logging boundary excludes bodies and exception messages/data. Diary responses use `Cache-Control: no-store, private`; the service worker has no fetch/cache handler.

The optional exact 1–128-character `Dagbogskode` uses ASP.NET Identity's versioned PBKDF2 password hasher. It does not supply encryption keys. SHA-256 hashes of random unlock grants are persisted and bound to owner, validated login session and protection revision. The raw grant and any draft exist only in tab memory. Account/session changes, logout, page reload, closing the diary and 15 minutes without foreground activity close the view and clear its content. Closing clears local content and the grant immediately; server locking continues as an observed best-effort background request so a stalled connection does not block navigation or cancel a shared authentication refresh. GETs and scheduler requests never renew a grant. User activity is checked separately and cannot revive an expired grant. Transient activity-request outages preserve the in-memory draft; confirmed authentication/diary denials and the independent local idle timer clear it. Today/date controls refresh the server-authoritative local day without silently moving the selected editor or replacing its draft. Five failed code/password-recovery attempts cause a persisted account-wide five-minute lockout shared across sessions and server restarts. All diary operations share a per-account gate in this single-server application; horizontal multi-server deployment would require a distributed serialization strategy.

A close request revokes only its captured grant within the same owner/login session, so a delayed close cannot invalidate a later unlock. Missing or malformed grants do not revoke other grants.

Changing/removing a code requires the current exact code and revokes every unlock grant atomically. Forgotten-code recovery requires a newly submitted, freshly verified **account password**, removes diary protection and revokes every grant. Existing account login alone cannot invoke recovery successfully. Recovery cannot restore lost encryption keys. Anyone who can verify the account password can reset the optional diary code by design. Content remains encrypted after code removal or recovery. Administrators have no diary-owner bypass.

## Retention and reminders

An entry expires at local midnight on the anniversary of its diary date, in the configured timezone at creation (default `Europe/Copenhagen`); February 29 maps to February 28 in the following non-leap year. Editing and later timezone changes do not extend that fixed stored deadline. Every read filters the UTC expiry immediately. The existing 30-second server worker runs restart-safe daily deletion with a persisted successful-run date; missed cleanup is retried after restart. Older backups can retain deleted entries until their own retention expires. Apply a backup retention policy and restrict backup access accordingly.

The independent diary-reminder preference defaults off. The existing scheduler adds the 20:00 local slot, with the existing 15-minute lateness window, persisted deduplication, inbox/outbox and retry rules. Saved whitespace-only text remains eligible. Pending push delivery rechecks the preference and saved text; unavailable keys suppress an uncertain reminder. Text is generic and the destination `/dagbog?iDag=true` is retained through normal login and diary unlocking. Device permission, configured VAPID credentials and an available server still determine phone delivery; no new secret/service is introduced for inbox reminders.

## Verification scope

Regression sources in `tests/FitnessApp.IntegrationTests/DiaryTests.cs` and `DiaryClientTests.cs` cover owner/admin isolation, endpoint gating, exact single/special-character codes, grant expiry and session binding, account-wide concurrent failure limits across repeated cooldown cycles, fresh-password recovery, revocation, ciphertext/purpose binding and key-ring reuse, conflicting saves/deletes, anniversary retention, daily cleanup, reminder suppression, recoverable activity outages and midnight/timezone changes with draft confirmation. The task permits a short solution build only; local test execution, app startup and browser QA are intentionally left to the user/CI. Use synthetic content for manual checks in both themes, including unsaved navigation, offline save retry, two-tab conflict, idle lock, reload/logout and reminder click-through.
